# Бэкенд: что он должен уметь и как с ним говорит сайт

Сайт статический: Next.js собирается в файлы и лежит на Pages. Всё, что
требует ключей или памяти между визитами, живёт на бэкенде. Фронт ходит
туда через один модуль — [`lib/api.ts`](../lib/api.ts), других выходов
наружу нет.

Адрес бэкенда берётся из `NEXT_PUBLIC_API_BASE`. Пока переменная пустая,
`lib/api.ts` отвечает моками, и сайт полностью работоспособен для показа —
ровно это сейчас и задеплоено.

---

## Зачем вообще бэкенд

| Задача | Почему нельзя на клиенте |
|---|---|
| Реквизиты по ИНН (DaData) | ключ DaData в браузере виден всем, и по нему спишут лимиты |
| Счёт в Контур.Эльбе | то же: ключ API Эльбы должен остаться на сервере |
| Заказы и их статусы | статику некуда записать, а статус живёт дольше сессии |
| Уведомления клиенту | почта и мессенджеры требуют секретов и подписи |
| Загруженные файлы (свой макет, фото подписи) | файл надо куда-то положить |

## Эндпоинты

Всё — JSON, UTF-8. Ошибки: код HTTP + `{ "error": "текст для лога" }`;
текст пользователю фронт подбирает сам.

### `GET /registry/{inn}`

Реквизиты по ИНН. На бэке — DaData (`findById/party`), ответ приводится к
нашему виду; исходный ответ DaData наружу не отдаём.

```json
{ "status": "found", "org": "Ромашка", "city": "Оренбург", "ogrn": "1105658001239" }
```

`status`: `found` | `notfound`. Контрольные цифры ИНН и ОГРН фронт
проверяет сам ([`lib/inn.ts`](../lib/inn.ts)), сервер этим не занимается.

Кэш на стороне сервера обязателен: один и тот же ИНН в конструкторе
запрашивается при каждом изменении поля.

### `POST /orders`

Создание заказа. Тело — то, что собрал конструктор:

```json
{
  "kind": "ooo",
  "situation": "ooo",
  "template": "ooo-gost-40",
  "values": { "name": "ООО «Ромашка»", "inn": "5610100213", "city": "Оренбург" },
  "mount": "trodat-46042-ideal",
  "urgency": "rush",
  "total": 990,
  "delivery": { "method": "courier", "address": "ул. Пролетарская, 10" },
  "pay": "invoice",
  "contact": { "name": "Иван", "phone": "+7…", "email": "…" }
}
```

Ответ:

```json
{ "id": "ord_7f3", "number": "000412", "invoiceUrl": "https://…/schet-000412.pdf" }
```

`invoiceUrl` появляется, когда `pay = invoice`: бэк создаёт счёт в Эльбе
через её API и отдаёт ссылку на PDF.

### `GET /orders/{id}`

```json
{ "id": "ord_7f3", "state": "in_work", "paid": false, "updatedAt": "2026-02-10T09:12:00Z" }
```

`state`: `new` → `accepted` → `in_work` → `ready` → `issued`, плюс
`canceled`. По этому же адресу страница «Заказ принят» опрашивает статус.

**Что сейчас на сайте.** Экран `/zakaz` уже есть и показывает состав
заказа, способ получения и оплату. Номер он пока придумывает сам
(`ЛП-ГГММДД-NNNN`) и хранит заказ в `sessionStorage`, чтобы экран
переживал перезагрузку. Когда появится `POST /orders`, номер должен
прийти из ответа, а `sessionStorage` останется только как кэш до первого
`GET /orders/{id}`.

Контакты в форме уже есть: имя, телефон и почта. Телефон уходит в виде
`+79123456789`, почта — как ввели. Телефон обязателен всегда, почта — при
оплате онлайн и по счёту: без неё некуда прислать ссылку на оплату, чек и
закрывающие. При оплате на месте почта необязательна, но если введена —
проверяется.

### `POST /leads`

Заявка со страницы услуги: `{ "service": "faksimile", "name": "…",
"phone": "…", "file": "…" }`. Ответ `{ "ok": true }`.

### `POST /uploads`

Свой макет печати и фото подписи. `multipart/form-data`, ответ
`{ "url": "…", "name": "signature.png", "size": 128400 }`. Ограничения:
PDF, PNG, SVG, CDR, JPEG; до 20 МБ.

### `POST /webhooks/elba`

Приём статуса оплаты от Эльбы. Проверяем подпись, помечаем заказ
оплаченным, дальше — уведомление клиенту.

## Уведомления о статусе

Событие — смена `state` или `paid`. Каналы по убыванию надёжности:

1. **Почта** — чек и счёт вложением, письмо на каждый переход статуса.
2. **Telegram** — если клиент оставил ник; бот пишет короткие статусы.
3. **SMS** — только «готово, забирайте» и «доставлено в ПВЗ»: дорого.

Мастеру — отдельный канал: новый заказ падает в общий чат мастерской с
кнопкой «взять в работу».

## Оплата

| Способ на сайте | Кто принимает деньги |
|---|---|
| «По счёту» | Контур.Эльба: счёт по API, статус по вебхуку |
| «Онлайн картой» | эквайринг (ЮKassa / Тинькофф / CloudPayments) — Эльба этого не умеет |
| «При получении» | касса в пункте выдачи |

При оплате физлицом нужен чек по 54-ФЗ — это онлайн-касса, а не Эльба.
Если платит организация по счёту, чек не нужен.

## Что учесть при разработке

- **CORS**: домен сайта (`imiron.ru`, потом `labpechatey.ru`) в белом списке,
  методы `GET, POST`, заголовок `Content-Type`.
- **Лимиты**: `/registry` — не чаще 10 запросов в минуту с адреса, иначе
  чужой скрипт выест лимит DaData.
- **Персональные данные**: имя, телефон и адрес — это ПДн. Хранить их в
  России, в форме — галочка согласия со ссылкой на политику.
- **Идемпотентность**: `POST /orders` принимает заголовок
  `Idempotency-Key`, чтобы двойной клик не создал два заказа и два счёта.
- **Состояние заказа — на сервере.** Сейчас оно живёт в React-контексте и
  теряется при перезагрузке; после появления бэка черновик заказа нужно
  сохранять по `id` и подхватывать по ссылке.
